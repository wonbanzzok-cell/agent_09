# 웹 개발 규칙 v1

웹 페이지 코드를 작성하거나 배포할 때는 항상 이 규칙을 적용한다. `developer` 에이전트는 코드를 쓰기 전에 반드시 이 파일을 읽는다.

## 우선순위

- 기준끼리 서로 다르면 다음 순서로 따른다.
  1. 사용자의 요청
  2. 이 규칙
  3. `references/web/<topic>/`의 웹 디자인 레퍼런스 분석
  4. 일반적인 모범 사례

## 파일 구조

- 모든 페이지는 순수 **HTML, CSS, JavaScript**로 만든다. 프레임워크와 빌드 단계는 쓰지 않으며, 정적 서버에서 `index.html`을 열면 바로 동작해야 한다.
- 버전 폴더 `output/web/<topic>/v<N>/` 안은 다음 구조를 따른다.

```
v<N>/
├── index.html       # 진입점
├── css/
│   └── style.css    # 모든 스타일
├── js/
│   └── main.js      # 모든 스크립트
├── images/          # 페이지에 쓰는 이미지
├── libs/            # 내려받은 외부 라이브러리 (필요할 때만)
│   └── <library>-<version>/
├── screenshots/     # 확인용 스크린샷 (desktop.png, mobile.png). 페이지에는 포함하지 않음
└── .nojekyll        # GitHub Pages가 모든 파일을 그대로 제공하게 함
```

- HTML, CSS, JS 파일은 페이지에 꼭 필요할 때만 더 추가하고, 위 폴더 안에 둔다.
- 모든 링크, 이미지, 스타일, 스크립트에는 **상대 경로**를 쓴다 (`/css/style.css`가 아니라 `css/style.css`). 그래야 GitHub Pages 하위 경로 `/<task_name>/`에서도 동작한다.
- 파일 이름은 하이픈을 쓴 영어 소문자로 짓는다.

## 코딩 규칙

- **HTML:** 시맨틱 태그(`header`, `nav`, `main`, `section`, `footer`), `h1`은 하나, 논리적인 제목 순서, 한국어 내용에는 `lang="ko"`, `<meta name="viewport">`, 페이지 `<title>`과 `<meta name="description">`을 쓴다.
- **CSS:** 색상, 폰트, 간격은 레퍼런스 분석의 추천 방향을 바탕으로 `:root`에 CSS 변수로 정의한다. 모바일 우선으로 쓰고 넓은 화면은 미디어 쿼리로 대응한다. 레이아웃은 Flexbox와 Grid로 잡는다. 인라인 스타일은 쓰지 않는다.
- **JavaScript:** 스크립트는 `body` 끝에서 불러오거나 `defer`를 붙인다. `const`와 `let`을 쓰고, 라이브러리에 필요한 것 외에는 전역 변수를 만들지 않는다. JavaScript가 실패해도 페이지 내용은 읽을 수 있어야 한다.
- **접근성:** 의미 있는 이미지에는 모두 `alt` 텍스트를 달고, 색 대비를 충분히 하며, 포커스 표시가 보이고 키보드로 조작할 수 있게 한다.
- **애니메이션:** `prefers-reduced-motion`을 존중해 움직임을 줄여 달라는 사용자에게는 애니메이션을 끄거나 줄인다. 애니메이션은 짧게 하고 읽기를 방해하지 않게 한다.
- **내용:** 자료의 실제 내용을 쓴다. 임시 문구를 남기지 않는다. 레퍼런스의 글, 로고, 브랜드 자산을 복사하지 않는다.
- **폰트:** 웹 폰트는 Google Fonts에서 불러와도 된다. 대체 폰트 목록을 항상 지정한다.

## 라이브러리

- 먼저 순수 CSS와 JavaScript로 해결한다. 애니메이션이나 효과에 꼭 필요할 때만 라이브러리를 추가한다 (예: GSAP, AOS, Swiper, Lottie).
- 라이브러리가 필요하면 묻지 않고 직접 설치한다.
  1. 정확하고 안정적인 버전을 고른다 (`latest`는 쓰지 않는다).
  2. 공식 릴리스, npm 레지스트리, cdnjs, jsDelivr에서 배포용 파일(예: 압축된 `.js`, `.css`)을 **내려받는다**.
  3. 라이브러리의 라이선스 파일과 함께 `libs/<library>-<version>/`에 저장한다.
  4. `index.html`에서 상대 경로로 연결한다. 실행 중에 CDN에서 라이브러리를 불러오지 않는다.
- 결과 폴더에서 `npm install`을 쓰지 않고, `node_modules/`는 절대 커밋하지 않는다.
- 설치한 라이브러리는 모두 사용자에게 보고한다: 이름, 버전, 내려받은 주소, 용도, 라이선스.

## 배포 (GitHub Pages)

- 완성한 페이지는 **사용자에게 먼저 묻지 않고** 바로 배포한다.
- **레포지터리 이름:** 작업명(`task_name`), 즉 작업의 `<topic>` 슬러그를 쓴다 (예: `csat-2027-checklist`). 작업 하나에 레포지터리 하나를 둔다.
- **소유자:** 로그인된 GitHub CLI 계정(`gh api user -q .login`)을 쓴다. 직접 적어 넣지 않는다.
- **공개 범위:** 무료 계정에서 GitHub Pages가 동작하도록 공개(public)로 만든다.
- **설명 표시:** 이 워크플로로 만든 레포지터리는 모두 설명 끝에 `[agent_09 web]`을 붙인다.

### 단계

1. `gh repo view <owner>/<task_name>`으로 레포지터리를 확인한다.
   - **없음:** `gh repo create <task_name> --public --description "<페이지 제목> [agent_09 web]"`으로 만든다.
   - **있고 설명이 `[agent_09 web]`으로 끝남:** 같은 작업의 이전 버전이다. 새 버전으로 갱신한다.
   - **있지만 표시가 없음:** 관계없는 레포지터리다. 건드리지 않는다. 멈추고 이름 충돌을 사용자에게 보고한다.
2. 버전 폴더(`screenshots/` 제외)를 **이 저장소 밖의** 새 임시 폴더로 복사한다. 저장소 안에 중첩 Git 레포지터리가 생기지 않게 하기 위해서다. 레포지터리가 이미 있으면 먼저 임시 폴더에 클론한 뒤, `.git/`을 제외한 파일을 새 버전으로 바꾼다.
3. 임시 폴더에서 `Deploy <task_name> v<N>` 메시지로 커밋하고, 커밋에 `v<N>` 태그를 붙인 뒤 `main` 브랜치와 태그를 push한다.
4. GitHub Pages가 아직 꺼져 있으면 `main` 브랜치 루트에서 켠다:
   `gh api -X POST repos/<owner>/<task_name>/pages -f "source[branch]=main" -f "source[path]=/"`
5. 빌드(`gh api repos/<owner>/<task_name>/pages/builds/latest`)의 상태가 `built`가 될 때까지 기다린 뒤, 브라우저로 `https://<owner>.github.io/<task_name>/`을 열어 스타일, 스크립트, 이미지와 함께 페이지가 뜨는지 확인한다.
6. 임시 폴더를 지운다.
7. 배포 링크와 레포지터리 링크를 Markdown 링크로 사용자에게 전달한다.

### 배포 안전 수칙

- 비밀 정보, 토큰, `.env` 파일, 개인정보는 절대 커밋하지 않는다.
- 레포지터리를 절대 삭제하지 않고, `[agent_09 web]` 표시가 없는 레포지터리에는 절대 force-push하지 않는다.
- 배포 단계가 두 번 시도해도 실패하면 멈추고 명령 출력과 함께 오류를 보고한다.

- 로컬에서 가로 1440px와 390px로 페이지를 확인한다: 레이아웃 깨짐, 화면 밖으로 넘친 글, 겹친 요소, 빠진 이미지, 콘솔 오류가 없어야 한다.
- 배포된 페이지도 같은 방법으로 확인한다.
- 보고 항목: 결과 폴더, 페이지 설계, 설치한 라이브러리(없으면 "없음"), 배포 링크, 레포지터리 링크.
